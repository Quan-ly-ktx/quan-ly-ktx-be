# KTX Hub backend architecture and database audit

**Audit date:** 2026-11-15
**Branch:** `refactor/erd-and-implemented-code`
**Scope:** Phase 1, repository/source audit only. No live PostgreSQL, Redis, OCI, or deployed API was inspected.
**Authoritative sources read:** [`docs/SRS.md`](../SRS.md) v3.4.1 FINAL; [`docs/Conceptual_ERD.md`](../Conceptual_ERD.md) v3.5 FINAL; [`docs/Logical-ERD.md`](../Logical-ERD.md) v3.6 FINAL. The explicit decisions in the audit task override conflicting document text. In particular, the target account statuses are **ACTIVE/LOCKED only**. The source working tree was clean before the audit.

## 1. Executive summary

The backend is an early functional slice, not a Phase 1 implementation. It has 16 of the 20 target tables in Flyway V1–V7, JPA entities for those 16, REST routes for authentication, room/bed, tenant administration, onboarding, contracts/documents, and vehicles, and a passing H2-based test suite. It has no renewal, room-code registry, notification, or vehicle-change-request table. Invoice, payment, expenses, maintenance, violations, dashboard, and most Tenant portal behavior have entity/repository shells but no operational service/API. See `src/main/resources/db/migration/V1__init_dorm_management_schema.sql:12-213`, `V6__add_contract_documents_and_refine_vehicles.sql:11-20`, and controller inventory below; target inventory: `docs/Logical-ERD.md:23-31,169-695`.

The highest risks are an incomplete onboarding transaction (no first invoice or day-01 rule), renewal overwriting historical terms, checkout assigning the wrong bed/vehicle states, no concurrency-grade uniqueness, and exposed/local or simulated file storage. The current tests encode several old rules and cannot validate Flyway because the test profile uses H2 `create-drop` and disables Flyway (`src/test/resources/application.yml:4-19`). **Readiness: ready to plan and begin a bounded refactor after confirming the data environment; not ready for Phase 1 release or frontend API integration.**

**Classification:** `MATCH` means the material schema and behavior audited conform; `PARTIAL` means some target elements exist; `MISMATCH` means the current shape or rule conflicts; `MISSING` means absent; `OBSOLETE` means a current element should be retired after reference/data checks; `UNVERIFIED` means source evidence cannot establish runtime state. Severity is separate from implementation priority (`P0`, `P1`, `P2`, `DEFER`). A missing Phase 1 feature is normally `HIGH/P1`, not automatically a blocker.

## 3. Database gap matrix: all 20 target tables

The comparison is **source-represented schema**, not a claim about any live database. Unless a row says otherwise, existing table IDs are UUID PKs with `gen_random_uuid()` in V1 and `GenerationType.UUID` in JPA; the target keeps UUID PKs, while `room_amenities` has a composite PK and `room_code_registry.code` is its PK (`docs/Logical-ERD.md:35-49,169-265`). Existing money columns are generally `numeric(12,2)`; target amounts are `numeric(14,0)`. Existing timestamps often lack target `updated_at`. Existing FKs and deletion rules are in V1/V6; target historical FKs generally use RESTRICT (`docs/Logical-ERD.md:695-738`). Each row names the target constraints and action; state transitions receive additional detail in §5. Path shorthand below resolves as follows: `V1`–`V7` are the matching files under `src/main/resources/db/migration/`; `entities/`, `enums/`, `repositories/`, `services/impl/`, `controllers/`, `security/`, `configs/`, and `dtos/` are under `src/main/java/com/uit/dormmanagement/`; document section references are to the three `docs/` files named at the top.

## 8. Security, authorization and files

1. **Public files are a direct privacy issue (BLOCKER/P0).** `SecurityConfig.java:93-95` grants anonymous `/uploads/**`, while `WebMvcResourceConfig.java:19-30` serves local files and `StorageConfig.java:29-34` defaults there. Contract and vehicle services return URLs (`ContractServiceImpl.java:220-229`, `VehicleServiceImpl.java:263-278`). FR-10/SRS §7.3/Logical §3.3.3 require private OCI objects and owner-checked links lasting at most 15 minutes. The OCI class is simulated (`OciObjectStorageServiceImpl.java:90-104`). Implement actual private storage and authorization before exposing production files; no public URL fields in API responses.
2. **Revocation is incomplete (HIGH/P0).** The filter checks a single Access JTI blacklist and current User status (`JwtAuthenticationFilter.java:51-70`), which helps lock a Technician. `revokeAllUserSessions` removes refresh tokens only (`TokenRevocationServiceImpl.java:69-79`), so other already-issued Access tokens remain valid after logout-all/change/reset password or unlock unless the account stays LOCKED. Add user-level token version/epoch or equivalent Redis revocation, verify in filter, and test all sessions (FR-22–24).
3. **Auth identifiers contradict BR-09 (HIGH/P0).** `AuthServiceImpl.java:296-304` accepts username, email, phone and does not look up Tenant by CCCD; `:217-245` forgot flow takes email only. Onboarding uses a fixed `Password123@` (`OnboardingServiceImpl.java:43,95-99,198-207`). Switch to CCCD Tenant/email Staff and random one-time credentials; avoid account enumeration and full identifier logging (`AuthServiceImpl.java:222-233`, `OnboardingServiceImpl.java:178-182`).
4. **Ownership must be implemented per new resource (HIGH/P1).** Current role annotations do not establish resource ownership. `/me` services resolve User→Tenant (`ContractServiceImpl.java:259-270`, `VehicleServiceImpl.java:182-233`), which is a reusable pattern. New Invoice/proof, Document, Vehicle Request, Ticket, Violation, Notification and roommate APIs must resolve owner and resident state on each read/write; after checkout allow only the specified history/proof actions (BR-11/FR-07,25–27).
5. **Upload validation is incomplete (HIGH/P0).** `ContractServiceImpl.java:273-287` checks extension and 10 MB only, then trusts `getContentType()` (`:209-213`). Vehicle upload has no type-specific rule and assumes both files (`VehicleServiceImpl.java:197-229`, `TenantRegisterVehicleRequest.java:9-12`). Validate real bytes/signatures, declared MIME and extension; enforce SRS max size, object privacy, and type-dependent plate/evidence fields. Reject invalid uploads before creating DB state.

### 14.4. Integrity Constraints & Database Logic Verified

1. **Active Occupancy Limits:**
   - At most 1 active contract per bed (`uq_contracts_active_bed`).
   - At most 1 active contract per tenant (`uq_contracts_active_tenant`).
2. **Date Alignment & Billing Invariants:**
   - Contract `start_on` must be 1st day of month (`ck_contracts_start_day`).
   - Invoice `billing_period` must be 1st day of month (`ck_invoices_billing_period_day1`).
   - ContractRenewal `effective_from` must be 1st day of month (`ck_contract_renewals_effective_day`).
   - At most 1 invoice per contract per billing period (`uq_invoices_contract_period`).
   - Exactly 1 confirmed payment receipt per invoice (`payment_transactions.invoice_id UNIQUE`).
3. **Contract Renewal & Document Safety:**
   - Contract renewal sequence uniqueness per contract (`uq_contract_renewals_sequence`).
   - Contract renewal period uniqueness per contract (`uq_contract_renewals_effective`).
   - Composite foreign key `fk_contract_documents_renewal` enforces document references a renewal belonging to the exact same contract.
   - Document type check enforces `RENEWAL_ANNEX` requires `renewal_id IS NOT NULL`, and non-annexes require `renewal_id IS NULL`.
4. **Facility Expenses & Operations:**
   - At most 1 `SALARY` expense per calendar month (`uq_facility_expenses_salary_month`).
   - Maintenance ticket assignee presence coupled with status lifecycle (`ck_maintenance_tickets_status_staff`).
   - Maintenance ticket completion requires resolution notes, resolution photo key, and timestamp (`ck_maintenance_tickets_completed`).
   - Replacement part positive quantity and non-negative unit cost.
   - Violation level & fine amount coupling (`ck_violations_fine_amount`).
5. **Vehicles & Notifications:**
   - At most 1 active vehicle (`PENDING_CARD`, `ISSUED`) per tenant (`uq_vehicles_tenant_active_quota`).
   - Card code uniqueness among `ISSUED` vehicles (`uq_vehicles_issued_card_code`).
   - At most 1 pending vehicle change request per tenant (`uq_vehicle_change_requests_pending_tenant`).
   - Notification `dedupe_key` uniqueness for non-null values (`uq_notifications_dedupe_key`).
